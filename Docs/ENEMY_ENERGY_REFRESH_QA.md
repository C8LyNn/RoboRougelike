# Enemy energy refresh allocation reduction

Enemy energy previously allocated arrays and LINQ iterators each time it searched for batteries and shields. The same active-child search now fills reusable lists, aggregates tier units and functioning shields, and clears references after each refresh. It does not cache component membership: mounted, disabled, detached, destroyed and newly added devices are still rediscovered. Enemy energy values, 25-unit shield reservation and other gameplay rules are unchanged.

Unity 6000.3.14f1 Editor with an actual spawned enemy carrying a battery; `ProfilerRecorder` measures whole-frame `GC Allocated In Frame` after warm-up. One isolated 1000-refresh sample before the change (`EnemyEnergy-Red3-20261108`) measured **330,878 bytes**, versus **7,708 bytes** in an idle frame. The comparable standalone sample afterwards (`EnemyEnergy-StandaloneFinal-20261108`) measured **7,708 bytes** in both the sample and idle frames. This demonstrates the result in these test frames, not universal zero allocation, an FPS improvement, or a Windows Player benchmark. Editor background allocations varied across other trials, so the permanent diagnostic reports values rather than asserting a hard whole-frame threshold.

`EnemyEnergy-Green-20261108`: **6/6 PASS**, exit 0. Tests include T2/T3 enemy batteries, full spawn charge, lost capacity on battery destruction, shield reservation and loss, real enemy battery damage, and player regenerator behavior during EMP and destruction. `EnemyEnergy-StandaloneFinal-20261108`: **1/1 PASS**, exit 0. Before the change the 1000-refresh diagnostic exceeded its temporary allocation budget (`EnemyEnergy-Red3-20261108`, 0/1, exit 2). The budget assertion was removed after the result because whole-Editor-frame background activity varies; the recorded failure is retained.

Raw XML, logs and exit codes: local `Artifacts/Local/` paths above. Windows Player, many-enemy frame time, complete Unity suites and manual play: NOT RUN. No change to `main` or `develop`.
