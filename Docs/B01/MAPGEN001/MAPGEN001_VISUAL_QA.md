## Executive assessment

R2 deliberately uses Cube primitives for floor, boundary, cover, obstacles and 7-degree pitched ramps, with matching primitive BoxColliders generated by `GameObject.CreatePrimitive(Cube)`. That is the right graybox strategy for initial physical QA: avoid polished models obscuring the true collision mesh. There is no current visible representation of start, finish, enemy spawn or checkpoint descriptors; the standalone demo camera is fixed after each generation. Existing colors are only applied through `MaterialPropertyBlock.SetColor("_BaseColor")`, so rendering depends on the runtime primitive's material/shader exposing this property; verify in the actual URP project.

The isolated B01-30 change creates a **demo-only non-colliding overlay** and a camera that follows the demo rover. No new art asset, material dependency or collider is required. Source math identifies two actual shape issues owned by B01-20 for later geometry rework.

## Prefab / mesh / pivot decision

**No new physical prefab is necessary**. Core R2 cubes already use center pivots, a BoxCollider matching each visible primitive, stable axis-aligned dimensions (except explicit X-rotated ramp), and an identity-oriented host in the demo. The user asked for *functional graybox*, not a new catalog of meshes. A separate heavy Blender/FBX pack would add dependencies and make physics QA harder. The B01-30 markers are transient Cylinder primitives parented under the generated root, with collider disabled+scheduled for destruction. They have their own visual pivot at the world-coordinate descriptor's floor XZ and never modify the planner's `MapElement`, geometry hash, accepted route or Rigidbody.

Demo-only support changed files relative to R2: `Runtime/MapGenDemo.cs` (hooks), `Runtime/MapGenDemoVisuals.cs` + `.meta` (marker/follow implementation), and this report. No prefab, material asset or pipeline package introduced.
