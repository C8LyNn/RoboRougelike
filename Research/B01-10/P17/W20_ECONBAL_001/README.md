## A concrete balance decision, not a fake game implementation

The current owner hypothesis is **one global free rebuild reservation per authenticated victory** and paid subsequent reservations. One *purchased* quote is a tuning variable; current original ECON #252 says 65–75% of purchase price is **a hypothesis, not final tuning**. Exact `100 Scrap purchase / 70 Scrap discounted rebuild` is hypothetical and makes comparisons auditable. Includes the original #252 epoch-zero bootstrap (initial single free coupon) **and** a zero-bootstrap alternate to reveal that policy's effect. The alternative `per_run` uses only one coupon for the entire run. Neither alternative is authorized for production based on these calculations alone.

`rebuild_balance.py` is an original deterministic Python 3.12 pure design simulator. It keeps one simulated wallet, one single-owner coupon for the entire run/epoch, ordered distinct attempt/victory identities, unique physical part IDs, reservations paid **before** the event reward, and restores pending reservations **only** after a modeled distinct successful event. Failed challenges do not reset free quota and cannot auto-heal. Parts are prioritized **mobility → weapon → other** for scarce coupons. First epoch bootstrap is optional. Cost is the integer truncated percentage (`purchase * quote_percent // 100`, must be 1..purchase-1). This is **not a physical CAS ledger**, cannot authenticate a real victory, cannot prove a real softlock, and cannot read from/save to any Unity host.

The independent `test_rebuild_balance.py` has **70 authored original executable tests** for the two policies, no/with bootstrap, free vs quoted paid, wins and losses, mobility prioritization under zero Scrap, no mid-event reward credit, duplicate victory ID fail-closed **within the model**, same physical part not billed twice, malformed parameters, deterministic seeds, and conservation. The *actual runtime anti-replay and two-service safety* belong exclusively to B01-22/B01-62 and do not inherit these tests' evidence.

## W21 R2 — confirmed deterministic model defect, real code correction

**RED source-level R1 bug discovered:** Original `run_plan` added parts destroyed by the CURRENT modeled encounter, reserved them, and then resolved *those same tickets* when the same event carried `won=true`. This violated the original B01-22 and HQ rule: **a part must await a later distinct genuine victory**. R1 unit test #1 even claimed all 24 parts restored by 12 hypothetical wins, when the two parts destroyed in the LAST win cannot be rebuilt without a thirteenth win. This was incorrect source-model behavior, not a live-game defect in B01-22.

**Actual R2 correction:** For each modeled valid event, (1) inspect pre-encounter deploy eligibility, (2) on a win resolve only tickets already reserved before the encounter and advance the genuine *modeled* win epoch, (3) register new damaged physical part IDs from that encounter, (4) reserve and debit NEW post-encounter requests for a future win, (5) add earned Scrap only after reservations, preserving the explicitly declared wallet ordering convention. With 12 scripted wins / two damaged each, total charged Scrap remains **840 vs 1610**, but **22 parts restored / 2 still reserved** (versus R1's incorrect 24/0). **No-bootstrap is now also 840** on this input because each damage event follows its current victory, while an initial LOSS requires paid reserve. All old positive test expectations affected are updated and distinct original regression tests added.

**P0 anti-softlock design investigation, not actual host logic:** New optional `blocks_deploy` part flag is explicit input testimony that the particular destroyed part is essential to the next encounter's `CanDeploy` contract. Neither every damaged wheel nor every weapon is automatically assumed fatal. `enforce_deploy_gate=True` refuses to count a scripted future WIN/reward/damage when a preceding marked essential 0HP part remains unavailable, **including when reserved**. The underlying 0HP vehicle CANNOT win the next battle to collect a delayed rebuild if no eligible fallback exists — a circular dependency absent from optimistic R1 accounting. `loaner_challenges=1` simulates one **NOT APPROVED** temporary weaker borrowed rig opportunity; it never immediately restores any owned 0HP part, does not grant extra real event IDs, and DOES NOT guarantee victory (a loaner defeat exhausts the one hypothetical lease). This is a **counterfactual feasibility/UX model**, NOT a proof that the actual game softlocks or an implementation of #154's candidate C.

**New executable original named tests #46–70 (25):** post-victory damage NEVER healed by its own event, later win closes only pre-existing tickets, explicit essential vs non-essential mobility, fee/slot order, no-bootstrap first win/loss distinction, critical-part-first allocation with no Scrap, modeled next-win reachability blocked by 0HP essential part, phantom scripted wins/rewards denied, one finite borrowed rig opportunity exhausted by failure, invalid/nonboolean flags and invalid temporary lease policies, unaltered old hypothetical 840/1610 monetary baseline. Total **70 actual Python source tests** to be verified on exact new HEAD across Windows and Ubuntu.

## W22 / R3 — Core / next-challenge eligibility before emergency continuation

**Independent B01-10 design discovery, not gameplay code:** Original R2 could offer a *hypothetical* one-shot borrowed robot whenever a mandatory component blocked normal deploy. This considered only damaged parts and spare loaner budget. It **did not model the two other compulsory policy-C preconditions from [#154](https://github.com/C8LyNn/RoboRougelike/issues/154): a still-living Core and a genuinely eligible NEXT challenge**. Without these, simulation can misleadingly suggest a recovery path after terminal Core destruction or when no next encounter exists. W22/R3 fixes this design-model overclaim, not an observed live Unity source flaw.

**New real original logic:** Every scenario attempt now accepts optional **strict booleans** `core_alive_after` and `next_challenge_available_after` (default both true for reproducible R2 compatibility). The previous attempt's post-state becomes a hard precondition for the NEXT attempted challenge. When Core is dead or the next challenge is unavailable, no scripted later victory is credited, no currency reward or damage is generated, and **no hypothetical loaner lease is consumed or offered**. Even when an essential 0HP item exists and loaner budget is one, Core dead or challenge unavailable overrides it. State is monotonically unavailable in this isolated bounded run model: there is deliberately no external host resurrection/new challenge API. A future game designer must model a distinct independently authorized challenge-unlock event instead of forcing fictional `won=true` through this gap. Repeated losing attempts after essential 0HP still never generate a free slot or complete old tickets. This prevents mathematically invalid positive result claims only.

**Explicit status for designers** `end_feasibility` is one of `RUN_CORE_DESTROYED_NO_LOANER`, `NO_ELIGIBLE_NEXT_CHALLENGE`, `ESSENTIAL_0HP_NEXT_WIN_INACCESSIBLE`, `ONE_UNAPPROVED_LOANER_COUNTERFACTUAL_AVAILABLE`, `ESSENTIAL_0HP_HOST_DEPLOY_UNVERIFIED` and `NORMAL_DEPLOY_ELIGIBLE_IN_MODEL_NOT_ACTUAL_WIN`. None is proof that real R3 CanDeploy passes, that a player can win or that the loaner is approved. Separate counts `blocked_core_attempts`, `blocked_no_challenge_attempts` and `contradicted_scripted_wins` expose optimistic scripted traces instead of manufacturing progress.

## W23 / R4 — time-of-credit affordability and terminal paid-ticket exposure

**This is an actual original B01-10 model feature, NOT production R3 economy.** The previous R3 simulator made a subtle *unapproved* assumption: post-combat earnings are credited **after** destroyed parts are quoted/reserved and the current wallet charged. Actual game reward settlement versus garage access is not verified. With 0 initial Scrap and one modeled winning battle giving 70 Scrap plus two 0HP parts, both after-combat pricing arrangements honor NEXT distinct WIN-only completion, but **`reward_timing="after_reservation"`** historically reserves one FREE ticket and denies one paid (wallet 70 after), whereas **`reward_timing="before_reservation"`** credits the earned 70 before two reservations and allows one FREE + one PAID (wallet 0 afterward). The new design setting is opt-in, backward compatible, and explicitly NOT an instruction to modify B01-22 authoritative charge/host or invent currency. Which ordering is in live R3 and is acceptable UX is a B01-00/B01-22/B01-13 owner decision after real source review/actual playtests; no claimed native fact.

**R4 real deterministic model code:** controlled enum `REWARD_TIMINGS=("after_reservation","before_reservation")`, new optional `reward_timing` in `run_plan`, `compare` and `synthetic_batch`, strict unknown-mode rejection; earnings are added exactly ONCE on an executed encounter, NEVER on an ineligible challenge, and no *current* winner can repair its just-destroyed parts regardless of reward timing. Explicit additional scenario output `reward_credit_before_order` enables side-by-side comparison without changing the baseline. **This is not a game integration or Save/Load transaction.**

**Second risk: cost booked but no reachable future victory.** R3 already knew if the ending Core was dead, no genuine next eligible challenge existed, or an essential 0HP blocker prevented deploying without the unapproved exhausted loaner. Such terminal modeled state can leave **already DEBITED** paid rebuild reservations awaiting a win the modeled run can never earn; prior reporting focused only on blocked mobility and underestimated the *economic* penalty. R4 now exposes `modeled_stranded_pending_count`, `modeled_stranded_paid_scrap`, and `modeled_stranded_free_tickets` (derived from actual accepted model queue tickets/charges; no invented debit or automatic refund). Example: after last synthetic victory creates two destroyed modules and no next eligible challenge, at wallet 70/paid quote 70, the run ends with 2 pending, **70 Scrap paid stranded** and one free reserved. This is a warning to revisit whether the garage may sell an unrecoverable deferred service, NOT a claim the native game charged it or that a refund is approved. A remaining prospective unapproved one-shot loaner means exposure currently classified *not proven stranded* even if the loaner is very weak; real player attempts needed.
